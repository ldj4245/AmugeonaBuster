# 아무거나 버스터

점심 메뉴를 고르고, 같이 먹을 장소를 정하고, 식후 커피 내기까지 한 곳에서 해결하는 직장인용 점심 도구입니다.

## 주요 기능

### 오늘의 식단

- 삼성 계열 구내식당 지점 검색 및 자주 보는 지점 저장
- 날짜 이동과 아침·점심·저녁·야식·전체 끼니 필터
- 코너별 대표 사진, 구성 반찬, 칼로리(kcal), 식단 조회 상태 표시
- 식단 코너별 별점 통계와 익명 한줄평 작성 및 조회

### 카카오톡 식단 알림

- 카카오 계정 연결 후 구내식당, 요일, 발송 시간 설정
- 설정한 시간에 맞춰 아침(09시 이전)·점심(09~13시)·저녁(13~20시)·야식(20시 이후) 식단을 카카오톡 나에게 보내기로 발송
- 휴무일이거나 해당 시간대 식단을 확인할 수 없는 날에는 임의의 메뉴를 보내지 않고 발송을 건너뛰며, 웹 화면에서는 미등록·조회 실패 상태를 구분해 안내

### 메뉴 투표

- 로그인 없이 닉네임만으로 방 생성
- 최근 3시간 동안 만든 방을 목록에서 검색하고 바로 참여
- `ROOM-XXXXXX` 코드와 공유 링크로 참여
- 후보 메뉴를 고른 뒤 참여자별 `좋아요` / `다음에 먹기` 투표
- 대기실과 투표 진행 상황은 WebSocket(STOMP)으로 실시간 동기화
- 한 명이라도 `다음에 먹기`를 선택한 메뉴를 우선 제외해 결정하고, 모든 후보에 비선호 표가 있을 때만 점수 합산(`좋아요 - 0.5 × 비선호`)으로 최종 메뉴 선정
- 같은 브라우저에서 다시 접속하면 참여 상태와 내 투표 복원
- 방장이 나가면 다음 참여자에게 방장 권한 위임
- 방장이 중간 마감하면 제출된 표 기준으로 메뉴 결정

### 위치 기반 식당 추천

- 장소를 검색하거나 현재 위치를 사용해 약속 장소 확정
- 선택한 좌표 반경 1km 안에서 우승 메뉴와 가까운 식당 검색
- 메뉴 검색 결과와 주변 보완 식당을 구분해 표시
- 식당 카드에서 거리, 주소, 카카오맵 상세·길찾기 링크를 제공하고 지도 마커에서 위치와 전화번호 확인
- 방장이 최종 식당을 확정하고, 길찾기와 약속 링크 공유

카카오 장소 리뷰를 그대로 가져오는 대신, 서비스 안에서 식단 코너별 별점과 한줄평을 직접 작성하고 공유합니다.

### 식후 커피내기

한 기기에서 2~8명이 바로 진행할 수 있는 여섯 가지 게임을 제공합니다.

1. **주사위 2개**: 두 주사위 합계가 높은 사람 또는 낮은 사람이 커피 담당
2. **핀볼 한 판**: 공이 도착한 참여자 칸으로 커피 담당 결정
3. **반응속도 대결**: 신호가 바뀌는 순간 눌러 기록 비교
4. **5초 맞추기**: 5초에 가장 가까운 사람이 승자
5. **지뢰 피하기**: 차례대로 칸을 골라 지뢰를 피하는 게임
6. **한 명 뽑기**: 참여자 중 한 명을 무작위 추첨

참여자 이름과 최근 결과는 사용하는 기기에 저장하며, 모바일에서는 게임을 고른 뒤 시작 버튼이 화면 하단에 계속 보입니다.

## 사용 흐름

```text
식단 확인 → 메뉴 투표 방 만들기 → 장소·후보 메뉴 선택
→ 참여자 초대 → 메뉴 투표 → 주변 식당 확인 → 커피내기
```

## 기술 스택

| 영역 | 사용 기술 |
| --- | --- |
| Backend | Java 21, Spring Boot 3.3, Spring Data JPA |
| Frontend | React 18, TypeScript, Vite, Tailwind CSS |
| 실시간 통신 | Spring WebSocket(STOMP), SockJS |
| Database | H2, PostgreSQL |
| 외부 연동 | Welstory 식단 API, Kakao OAuth·메시지·Local·Maps API |
| 테스트 / CI | JUnit 5, ArchUnit, GitHub Actions |

## 프로젝트 구조

```text
backend
├── domain                  # 방, 메뉴, 투표, 식단 후기 도메인 모델과 규칙
├── application             # 유스케이스와 입출력 포트
└── adapter
    ├── in                  # REST 컨트롤러, WebSocket, 알림 스케줄러
    └── out                 # JPA 영속성, 카카오·웰스토리 외부 연동

frontend
└── src/features
    ├── meals               # 식단 조회와 코너별 한줄평
    ├── rooms               # 메뉴 투표 방과 주변 식당 지도
    ├── games               # 커피내기 게임 6종
    └── settings            # 카카오톡 식단 알림 설정
```

백엔드는 메뉴 투표 규칙과 외부 API·저장소를 포트와 어댑터로 나눠 관리하며, ArchUnit 테스트로 계층 간 의존 방향을 검사합니다. 식당 검색이나 저장 방식이 바뀌어도 도메인 투표 규칙을 건드리지 않고 어댑터만 교체할 수 있습니다.

## 트러블슈팅

### 2026-10-31

#### 단일 코스 식단에서 카카오톡 알림 실패 및 구독 자동 해지 문제

- **문제**: 카카오톡 나에게 보내기는 여러 코스를 한 번에 보여주기 위해 `list` 템플릿으로 구현해 두었습니다. 그런데 카카오 `list` 템플릿은 항목을 최소 2개 이상(2~3개) 요구하기 때문에 아침이나 저녁처럼 코스가 1개만 나오는 날에는 카카오 API가 `400 Bad Request`를 반환했습니다. 기존 알림 서비스는 발송 실패를 모두 액세스 토큰 만료로 간주해 토큰 갱신 후 재발송까지 실패하면 해당 사용자의 알림 설정(`isEnabled`)을 `false`로 꺼버리고 있었습니다.
- **해결**: 코스가 1개 이하일 때는 대표 이미지가 없어도 보낼 수 있는 `text` 템플릿으로 분기하고, 2개 이상일 때만 `list` 템플릿을 사용하도록 나눴습니다. 또한 카카오 API 호출 결과를 `SENT`, `UNAUTHORIZED`, `FAILED`로 분리해 실제 `401` 인증 오류나 리프레시 토큰 만료가 아닌 일시적 전송 실패에서는 사용자의 알림 구독이 꺼지지 않도록 수정했습니다.

#### 일부 끼니 조회 실패(PARTIAL) 시 정상 끼니 알림 누락 및 야식 시간대 분리

- **문제**: 하루 식단을 가져올 때 아침·점심·저녁·야식 네 끼니를 병렬로 호출하는데, 그중 야식 한 끼만 응답이 지연돼도 전체 식단 상태가 `PARTIAL`로 표시됩니다. 기존 스케줄러는 전체 상태가 `AVAILABLE`일 때만 알림을 보내도록 막아 두어, 점심 식단이 정상적으로 조회됐는데도 점심 알림이 발송되지 않는 문제가 있었습니다. 또한 시간대 필터가 13시 이후를 모두 저녁으로 묶고 있어 20시 이후 야식 알림이 동작하지 않았습니다.
- **해결**: 시간대 필터를 20시 기준으로 저녁(13~20시)과 야식(20시 이후)으로 나누고, 전체 상태가 `PARTIAL`이더라도 발송 대상 시간대의 코스가 존재하면 정상 발송하도록 조건을 바로잡았습니다.

#### 소수점이 포함된 칼로리 문자열 파싱 오류

- **문제**: 일부 지점 식단 데이터에서 칼로리가 `"720.5"`처럼 소수점을 포함해 내려오는 경우가 있었습니다. 기존 파서는 숫자가 아닌 문자를 모두 지우는 정규식(`[^0-9]`)을 거친 뒤 정수로 변환하고 있어서 소수점이 사라진 `"7205"`가 되어 `7205 kcal`로 표시됐습니다.
- **해결**: 정규식으로 정수부와 소수부를 함께 추출해 실수로 파싱한 뒤 반올림하도록 수정해 `"720.5"`나 `"1,050 kcal"` 같은 입력이 모두 실제 수치에 맞게 변환되도록 고쳤습니다.

#### 서버 타임존(UTC) 차이로 오전 9시 이전에 전날 식단이 조회되던 문제

- **문제**: 클라우드 서버의 기본 타임존이 UTC로 설정되어 있다 보니 한국 시간 오전 9시 이전에는 `LocalDate.now()`가 하루 전 날짜를 반환했습니다. 예를 들어 화요일 오전 8시 50분에 이전 알림 링크를 눌러 식단을 조회하면 화요일이 아니라 월요일 식단이 뜨는 문제가 발생했습니다.
- **해결**: 식단 조회 서비스, 알림 스케줄러, 날짜 파싱 로직 전반에 `ZoneId.of("Asia/Seoul")`을 명시해 실행 서버의 기본 타임존과 관계없이 한국 날짜와 시간 기준으로 동작하도록 통일했습니다.

#### 카카오맵 인포윈도우 DOM XSS 및 한줄평 식별자 노출 보완

- **문제**: 주변 식당 지도의 마커 인포윈도우를 HTML 문자열 결합으로 렌더링하고 있어 외부 장소 데이터에 스크립트 구문이 포함될 경우 실행될 여지가 있었고, 상세 링크도 URL 스킴 확인 없이 열리고 있었습니다. 또한 익명 한줄평 조회 API가 도메인 모델을 그대로 직렬화해 중복 방지용 `userFingerprint`가 응답에 노출되고, 클라이언트가 요청마다 식별값을 바꾸면 같은 세션에서도 중복 등록이 가능한 구조였습니다.
- **해결**: 인포윈도우는 문자열 템플릿 대신 `document.createElement`와 `textContent`로 DOM 노드를 직접 구성하도록 바꾸고 `http`/`https` 스킴만 링크로 허용했습니다. 한줄평 API는 식별자를 제외한 전용 응답 DTO로 분리하고, 식별값을 서버 세션에 고정하는 동시에 DB에도 `(식당명, 날짜, 코스명, 식별자)` 복합 Unique 제약을 추가해 중복 작성을 막았습니다.

#### 웰스토리 토큰 만료 시 200 OK 빈 응답이 내려오던 문제

- **문제**: 외부 식단 API를 연동할 때 처음에는 `401`이나 `403` 상태 코드가 오면 재로그인하도록 작성했습니다. 실제로 운영해 보니 토큰이 만료된 뒤에도 HTTP 상태 코드는 `200 OK`로 내려오고 응답 본문만 비어 있거나 `data` 필드가 빠진 JSON이 반환되는 경우가 있었습니다. 이 상태에서는 재로그인 분기를 타지 못해 휴무일이 아닌데도 식단이 비어 있는 것처럼 보였습니다.
- **해결**: 응답 본문이 비어 있거나 `data` 배열이 없는 비정상 페이로드도 세션 만료로 판단해 토큰을 재발급받고 한 번 더 조회하도록 고쳤습니다. 여기에 JWT의 `exp` 클레임을 읽어 만료 30초 전에 미리 토큰을 갱신하도록 바꾸고, 외부 API가 일시적으로 응답하지 않을 때는 최근 6시간 안에 정상 조회된 캐시가 있으면 이를 대신 반환하도록 보완했습니다.
