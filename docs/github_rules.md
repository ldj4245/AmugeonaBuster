# 🐙 GitHub 협업 및 브랜치 전략 규칙 가이드라인

본 문서는 프로젝트의 형상 관리, 코드 리뷰 문화, 그리고 릴리즈의 안정성을 엄격히 통제하기 위한 **Git 및 GitHub 협업 가이드라인**입니다.
이 가이드는 기능 개발의 추적성을 보장하고 커밋 로그를 깔끔하게 유지하여 협업 생산성을 높이는 것을 목적으로 합니다.

---

## 1. Git 브랜치 전략: GitHub Flow

우리는 배포 및 상용화 가능한 고품질의 코드만을 관리하기 위해 **GitHub Flow** 전략을 따릅니다.

```
       [ main ] ───────────────────────────────────────────► (항상 빌드 및 배포 가능 상태)
          │
          │ branch off
          ▼
     [ feature/#12-lobby-ws ] ───► Commit ───► Push ───► PR Open
                                                           │
                                                           │ Code Review & Merge
                                                           ▼
       [ main ] ───────────────────────────────────────────
```

### 브랜치 생명주기 규칙
1.  **`main` 브랜치:**
    *   언제든 배포 및 로컬 실행이 가능해야 하는 프로덕션 브랜치입니다.
    *   **규칙:** `main` 브랜치에 직접적인 push는 금지됩니다. 반드시 PR(Pull Request)을 거쳐 병합되어야 합니다.
2.  **`feature` 브랜치 (기능 개발):**
    *   작업 단위별로 `main` 브랜치에서 분기하여 개발을 진행합니다.
    *   **명명 규칙 (Branch Naming):** `feature/이슈번호-간단한기능설명` (모두 소문자 사용, 띄어쓰기는 하이픈 `-` 사용)
        *   *올바른 예:* `feature/#14-create-room`
        *   *올바른 예:* `fix/#39-websocket-reconnect`
        *   *잘못된 예:* `feature/RoomRegister` (이슈번호 누락, 대소문자 혼용)

## 2. 커밋 메시지 규칙 (Commit Message Convention)

의도가 명확한 커밋 메시지는 히스토리 역추적과 롤백 작업 시 매우 중요합니다. 우리는 Angular Commit Message Guidelines를 변형한 방식을 채택합니다.

### 커밋 메시지 기본 포맷
```
[타입] 제목 (#이슈번호)
```

### 대표적인 커밋 타입 (Type)
*   `feat`: 새로운 기능 구현 및 요구사항 개발
*   `fix`: 버그 수정 및 예외 상황 대응
*   `docs`: 문서 수정 (README.md, docs/*.md, 주석 등)
*   `style`: 코드 포맷팅, 세미콜론 누락 수정 등 (코드 비즈니스 로직 변경 없음)
*   `refactor`: 비즈니스 로직 리팩토링 (가독성 향상, 아키텍처 규칙 준수 개선 등)
*   `test`: 테스트 코드 추가 및 수정 (ArchUnit 테스트 추가 등)
*   `chore`: 빌드 업무 수정, 패키지 매니저 설정(build.gradle), 라이브러리 추가 등

### 좋은 예시 (Good Examples)
*   `feat: 방 생성시 카카오 로컬 API 호출 기반 주소 정보 연동 (#12)`
*   `fix: 웹소켓 세션 종료 시 ConcurrentHashMap 인메모리 메모리 누수 버그 해결 (#45)`
*   `docs: 헥사고날 아키텍처 규칙 문서 내 ArchUnit 예시 추가 (#3)`
*   `refactor: Room 도메인 내부 투표 합산 순수 비즈니스 로직 분리 (#21)`

## 3. Pull Request (PR) 및 코드 리뷰 규칙

코드 병합 전, 코드의 무결성과 아키텍처 규칙 준수를 점검하기 위해 반드시 **Pull Request** 작성을 강제합니다.

### PR 기본 규칙
1.  **빌드 및 테스트 확인:** PR을 오픈하기 전 로컬 환경에서 `./gradlew build`를 실행하여 컴파일 에러 및 ArchUnit/단위 테스트에 이상이 없는지 선검증합니다.
2.  **작업 내용 기술:** 변경된 사항, 구현에 사용된 핵심 설계, 테스트 검증 결과를 상세히 적습니다.
3.  **셀프 리뷰 필수:** PR을 작성한 유저는 스스로 변경 코드 줄(Diff)을 한 줄씩 훑어보며 남겨진 디버깅용 로그(`System.out.println` 등)나 임시 주석이 없는지 체크합니다.

## 4. 실전용 PR 템플릿 마크다운 명세

프로젝트 루트 하위의 `.github/pull_request_template.md`에 아래의 내용을 저장하여 사용자가 PR을 올릴 때마다 이 체크리스트를 자동 출력하게 유도합니다.

```markdown
## 📌 개요 (Description)
- 작업한 이슈 번호: #이슈번호
- 주요 변경 사항 및 구현 목적에 대한 간략한 요약을 기술해 주세요.

## 🛠️ 주요 변경 사항 (Key Changes)
- [ ] 헥사고날 아키텍처 패키지 규칙에 맞추어 레이어가 적절히 분리되었나요?
- [ ] `domain` 레이어에 외부 프레임워크 import가 침범하지 않았나요?
- [ ] 데이터베이스(Entity)와 도메인 모델 간 Mapper가 올바르게 작동하나요?

## 🧪 테스트 결과 및 검증 (Testing Results)
- 구현된 기능을 검증하기 위해 수행한 테스트 방법 및 결과를 기술해 주세요. (예: 로컬 웹소켓 연결 성공 캡쳐, JUnit 성공 결과 등)
- [ ] 로컬 빌드(`gradlew build`)가 에러 없이 성공하였나요?
- [ ] `ArchUnit` 아키텍처 규칙 검증 테스트를 통과하였나요?

## 📝 셀프 체크리스트 (Self Checklist)
- [ ] 필요 없는 디버그 로그(`System.out.println`)는 제거했나요?
- [ ] 불필요한 주석이나 미사용 import는 정리했나요?
```
